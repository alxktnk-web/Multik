## Цель и границы

Исследовать предоставленные владельцем примеры плёночной мультиэкспозиции и улучшить характер изображения Multik: смешивание, тон, цвет, света, тени и красное гало. Работать в существующем TypeScript/WebGL2-приложении. Не переписывать приложение и не создавать другой редактор.

**Этот чат не меняет интерфейс вообще.** Нельзя менять DOM, CSS, экраны, расположение/видимость/состав кнопок, иконки, подписи, жесты, навигацию, импорт, диалоги, сохранение или пользовательский процесс экспорта. Внешний вид фотографии внутри canvas/JPEG — предмет задачи; оформление самого canvas и элементы вокруг него — интерфейс.

Не переименовывать и не переназначать существующие инструменты. Нельзя обойти запрет, изменив общую модель так, что в UI автоматически появятся новые параметры или изменятся диапазоны/чувствительность/смысл прежних controls.

Если для алгоритма нужен UI:

1. Прочитать [UI_CONTRACT.md](UI_CONTRACT.md) — подробное описание текущего интерфейса.
2. Добавить предложение по шаблону в [UI_REQUESTS.md](UI_REQUESTS.md), статус `proposed`.
3. Продолжить независимую математику и тестовый прототип с явно задокументированными фиксированными значениями, если это возможно. Если без нового UI безопасная интеграция невозможна, оставить соответствующую часть экспериментальной и описать зависимость.
4. Не реализовывать предложение и не считать запись согласованием. UI реализует другой чат по отдельному поручению владельца.

## Исходный конвейер v8

Проверить фактический код перед правками; ниже ориентир по v8, не замена чтению.

1. Изображения декодируются браузером; исходные текстуры загружаются как `SRGB8_ALPHA8` в `resources.ts`. Их sampling уже возвращает линейный RGB. **Не декодировать sRGB второй раз.**
2. Геометрия источника/слоя/кадра общая для preview и tiled JPEG; перенос и масштаб слоя не являются цветовыми эффектами.
3. В `shaders.ts` линейный свет A/B складывается с gain каждого слоя и balance. Это не opacity/multiply и не усреднение двух sRGB-картинок.
4. Маски красного гало выделяются из каждого источника до сложения, размываются и следуют геометрии источника. Средние по яркости A/B не должны давать ложный halo только от яркости суммы.
5. Profile 2: экспозиция, highlight shoulder после luminance .75, переход очень ярких областей к белому, gamut compression, sRGB transfer и умеренная S-кривая .35; затем существующий user contrast. Изучить порядок операций, не копировать формулы из описания вслепую.
6. Другие декоративные засветки/grain/bloom по умолчанию выключены. Не добавлять их в default без отдельного согласования владельца.
7. Preview и `Renderer.exportImage()` используют один алгоритм. JPEG — явная производная выбранной композиции, не источник истины.

## Контракт данных и профилей

- Не удалять/перекодировать оригиналы, не сбрасывать плёнки, проекты, правки, seed, revision, геометрию или IndexedDB ради нового вида.
- У каждой пары свои правки. Существующая экспозиция/balance/contrast/halo остаётся управляемой теми же controls с теми же диапазонами, default-значениями и направлениями жестов.
- Новый художественный алгоритм, меняющий результат при тех же параметрах, оформить как отдельную версию профиля. Сохранить доступный reference profile 2 для A/B и старых v8-композиций; не переопределять version 2 молча.
- Сейчас `copyComposition()` в `model/types.ts` нормализует profile 1 к 2, а validator разрешает 1/2. Учесть оба места при добавлении версии. Не заменять это безусловным переводом всех записей в новую версию.
- Для экспериментального профиля явно описать, где он применяется: тестовый harness, новые композиции или ещё не подключённый кандидат. Старые v8-композиции не переводить автоматически. Переключатель профилей в приложении — только предложение в UI_REQUESTS.md.
- Ключи производных/thumbnail/cache должны учитывать профиль и параметры. Старый thumbnail нельзя выдавать за результат нового алгоритма. Если это требует изменения UI-файла, зафиксировать зависимость; не обходить ограничение.
- Не обещать, что старая v8 прочитает записи нового профиля. Описать обратимость и возможный forward fix. Безопасный эксперимент и отключённая публикация важнее быстрого включения нового профиля всем.

## Производительность и экспорт

- Во время жестов: никаких JPEG/toBlob, readPixels, CPU ImageData, DB writes, повторного decode/upload неизменных источников или shader compilation.
- Сохранить rAF latest-state, ограниченные cache/texture budgets и освобождение ресурсов. Параметрические halo masks могут перестраиваться на GPU по текущему coalescing-контракту; не вводить аллокации на каждом движении.
- Общая математика preview/export, tiled/monolithic parity, одинаковые profile/seed/transform; halo не обрезается границами tiles и источника.
- Экспорт получает immutable snapshot; отмена/context loss не уничтожают draft и готовые исходники. Не менять workflow Save to Photos.
- Не объявлять плавность, цвет HEIC/HDR/P3 или Safari проверенными по Chromium. Устройство владельца: iPhone 16 Pro; iOS сообщена как «27.01», аппаратная приёмка не завершена.

## Как исследовать и сдавать результат

1. Сохранить выводы анализа референсов в IMAGE_ALGORITHM.md: отдельно наблюдаемые признаки, гипотезы о плёнке/сканировании и художественные решения. Не выдавать внешний вид готовой фотографии за достоверное восстановление физического процесса.
2. Разделить влияние наложения двух сцен, экспозиции, тональной кривой, цвета, halo и обработки скана. Описать формулы, цветовые пространства, порядок операций, параметры, диапазоны устойчивости и выбранные defaults.
3. Сравнить неизменённый profile 2 с кандидатом на одинаковых источниках/парах/геометрии/seed. Нужны чёрные/серые/белые поля, ступени экспозиции, насыщенные цвета, локальные яркие объекты и несколько разнородных фото. Не подгонять look только под одну красивую пару.
4. Приложить до/после с подписями профилей и параметров. Исследовательские contact sheets допустимы как отдельные артефакты, но не как новый экран приложения. Не коммитить пользовательские фото или чужие референсы в публичный репозиторий без разрешения; для git использовать синтетические/разрешённые fixtures.
5. Выполнить `npm test`, `npm run build`, `npm run test:lighttable:browser`, `npm run test:lighttable:export`, `npm run test:lighttable:gestures`. При изменении cache — `npm run test:lighttable:cache`; при изменении типов/валидации — data/workspace suites. Честно отметить неисполненные проверки и причины.
6. Не увеличивать tolerance и не удалять assertions только ради PASS. Обоснованное изменение ожидаемого цвета сопровождать reference/численным объяснением; гарантии сохранности/геометрии/экспорта сохраняются.
7. Обновить PROGRESS.md: SHA базы, своя ветка, изменённые файлы, checks, A/B-артефакты, ограничения, связанные UI request IDs. Отметить «кандидат, не опубликован»; не переписывать текущий статус production как будто кандидат уже принят.
8. Передать ссылку на commit/PR, сводку «что изменилось в картинке», доказательство отсутствия UI-правок и точные зависимости от будущего UI. Самостоятельно не объединять и не публиковать.

Если анализ уже выполнен в этом чате, не начинать его заново: перенести выводы и формулы в указанную структуру и проверить их применимость к существующему pipeline.
