# Предложения алгоритмического направления к интерфейсу

Создано 20.10.2026. Связанные документы: [ALGORITHM_HANDOFF.md](ALGORITHM_HANDOFF.md), [UI_CONTRACT.md](UI_CONTRACT.md).

Это очередь предложений, **не разрешение изменять UI**. Чат алгоритма добавляет подробные записи; владелец принимает решение, отдельный чат интерфейса реализует согласованное. Для новых предложений использовать статус `proposed`. Отсутствие ответа не означает согласие.

Статусы: `proposed` → `accepted` / `rejected` / `deferred`; после отдельной реализации — `implemented`. В `accepted` записать решение/поручение владельца; в `implemented` — commit/PR и проверки. Не помечать предложение согласованным от имени владельца.

## Очередь

Пока предложений нет. Никаких новых UI-параметров или изменений взаимодействия этим документом не утверждено.

## Шаблон записи

Скопировать ниже, назначить следующий свободный `UI-ALG-001`, `UI-ALG-002` и т. д. При параллельных ветках проверить ID перед объединением. Одно предложение — одна запись; сохранять историю обсуждения.

```md
## UI-ALG-001 — краткое название

- Статус: proposed
- Дата:
- Автор/направление: алгоритм изображения
- Ветка / commit / PR:
- Связанный профиль и раздел IMAGE_ALGORITHM.md:
- Нужен для работы алгоритма или является необязательным удобством:

### Причина
Что в изображении нужно контролировать, почему существующего инструмента
недостаточно, конкретный пример/ссылка на разрешённый A/B-артефакт.

### Пользовательское поведение
Какой экран/группа Pro, как человек находит действие, английские label/aria-label,
значок как предложение. Что остаётся в обычном режиме.
Portrait/landscape, управление одной рукой, VoiceOver/keyboard.
Никакой реализации в этом PR алгоритма.

### Контракт алгоритма
Точное имя API/поля, тип, единицы, диапазон, default и нейтральное/off-значение.
Линейная/логарифмическая шкала, дискретность, clamp.
Что изменяется в светах/тенях/цвете и как это взаимодействует с прежними
exposure/balance/contrast/halo. Нужен ли отдельный профиль.

### Жесты и состояние
One-axis или явно выбранный XY, назначение осей и направление роста.
Поведение tap, drag, cancel, pinch, повторного открытия, Undo.
Привязка к паре/проекту/глобальным prefs; никаких скрытых глобальных правок.
Точная граница сохранения, поведение при ошибке записи.

### Совместимость и стоимость
Defaults для старых записей, версия профиля, отсутствие DB migration/потери данных.
Влияние на preview/export/cache/thumbnail; uniform или rebuild, оценка бюджета.
Как сохраняется готовый JPEG и snapshot; эффект при halo=0/других краевых значениях.

### Работа без изменения UI
Какое фиксированное значение/тестовый API используется сейчас.
Что готово независимо, что заблокировано. Можно ли проверить кандидат без
нового пользовательского control. Не включать скрытый новый жест или кнопку.

### Критерии приёмки для UI-чата
Наблюдаемые сценарии и ожидаемые результаты, включая ошибки,
per-pair isolation, Undo, no-save-on-lift и preview/JPEG parity.
Что проверить именно на iPhone.

### Решение и реализация
Пока не согласовано. Заполняется владельцем/чатом UI после отдельного поручения:
дата, решение, commit/PR, выполненные проверки и открытые ограничения.
```
